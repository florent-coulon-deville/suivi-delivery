# Contexte pour Claude Code

## Projet

Application **« Suivi de la delivery »** (nom technique : `suivi-delivery`) : suivi des mises en production (MEP), qui remplace un suivi prévu sous Excel.

- **Noms** : titre affiché « Suivi de la delivery » ; noms techniques `suivi-delivery-*` (paquets, images publiées ; sur le poste, docker-deploy suffixe tout en **`-local`** : conteneurs et images `suivi-delivery-{postgres,liquibase,keycloak,backend,frontend}-local`, réseau `suivi-delivery-local`, volume `suivi-delivery-postgres-local`, choix de l'utilisateur ; base et utilisateur `suivi_delivery`). « MEP » reste le terme métier dans les textes. Anciens noms : release-management, suivi-mep.

- **Cible de déploiement** : OpenShift.
- **Stockage** (depuis 0.4.0) : **PostgreSQL**, une vraie table par objet (`app/storage_postgres.py`), mêmes opérations que le stockage en mémoire (`app/storage.py`, `MemoryStorage`, utilisé sans `APP_DB_HOST` : tests, essais). Pas d'ORM (psycopg 3 + psycopg-pool). Une transaction par requête (`app/transactions.py`, commit juste avant la réponse), **une écriture à la fois** (verrou `pg_advisory_xact_lock`), essai de cohérence dans un savepoint ; plusieurs exemplaires de l'API possibles. `IntegrityError` de la base → 409 (filet de sécurité). **Structure gérée par Liquibase 4.33.0** (choix de l'utilisateur, qui veut apprendre l'outil ; 4.x car seule version en Docker Hardened Image, licence Apache 2.0) : `liquibase/changelog/` (SQL formaté, `main.yaml` liste les fichiers ; **tables avec leurs seules colonnes** (001), puis chaque contrainte **nommée en `alter table … add constraint`** : `pk_` (002), `uq_` / `ck_` (003), `fk_` (004), index `ix_` (005), demande de l'utilisateur ; **ne jamais modifier un changement appliqué**, toujours en ajouter un, avec `--rollback` ; seule exception : historique **réécrit à neuf** au passage à Keycloak, avant toute mise en production, décision de l'utilisateur : 001 à 005, 15 tables, bases d'avant à recréer) ; colonne `trigram` des applications (code de 3 caractères), **schéma `suivi_delivery`** pour nos tables (`currentSchema` dans l'URL Liquibase, `search_path` de l'API, `APP_DB_SCHEMA`), schéma `keycloak` pour Keycloak (son propre utilisateur), `public` vide (décision de l'utilisateur : une seule base), image `suivi-delivery-liquibase` (module **`liquibase/`** à la racine : `Dockerfile` = `dhi.io/liquibase:4.33.0-debian13`, qui inclut le connecteur `postgresql` 42.7.12 (plus d'étape Maven, choix de l'utilisateur), + `changelog/` dans `/liquibase/changelog` (`LIQUIBASE_SEARCH_PATH`)) ; module **`postgres/`** (`Dockerfile` = `FROM dhi.io/postgres:18.6-alpine3.24` + point d'entrée `start.sh` (l'image durcie ne lance pas `/docker-entrypoint-initdb.d` et refuse un utilisateur inconnu : `start.sh` déclare l'utilisateur au hasard d'OpenShift dans `/tmp/passwd`, vers lequel renvoie `/etc/passwd`, puis au premier démarrage fait initdb + createdb et lance nos scripts sur un serveur provisoire sans réseau ; données dans `18/data`, utilisateur 70 hors OpenShift) + `initialization/01-schemas.sh`, qui crée au premier démarrage le schéma de nos tables, l'utilisateur et le schéma de Keycloak : Liquibase ne sait pas créer son propre schéma), Liquibase lancé **avant** l'API (docker-deploy, initContainer Helm, CI). L'API ne crée aucune table : elle vérifie seulement qu'elles existent. Guide : [docs/postgresql.md](docs/postgresql.md). Plus de reprise d'un ancien fichier SQLite (supprimée : rien n'a jamais été installé, décision de l'utilisateur).

Voir [README.md](README.md), [docs/comprendre-le-code/](docs/comprendre-le-code/README.md) (guide du code, à tenir à jour), [docs/architecture.md](docs/architecture.md), [docs/keycloak.md](docs/keycloak.md), [docs/frontend.md](docs/frontend.md), [docs/modele-de-donnees.md](docs/modele-de-donnees.md), [docs/api.md](docs/api.md), [docs/deploiement.md](docs/deploiement.md), [docs/glossaire.md](docs/glossaire.md) (mot métier → nom dans le code) et [docs/git.md](docs/git.md) (branches, PR, ménage des branches fusionnées) et [docs/ci.md](docs/ci.md) (CI).

## Préférences de l'utilisateur (à respecter)

- Répondre **en français**, de façon concise et directe. Une seule question à la fois si une précision est nécessaire.
- **Toujours demander validation avant d'agir** : écrire ou modifier du code, faire un choix technique, lancer une commande qui a un effet (git, docker…). Proposer, expliquer, attendre le « ok », puis agir.
- **Parler métier, pas technique**, et rester sur la forme générale : ne pas entrer dans les détails tant que l'utilisateur ne le demande pas.
- **Avancer par petites étapes simples**, que l'utilisateur comprend. Pas d'architecture complexe : il a explicitement refusé l'ancienne architecture en couches (domaine / data / api, Alembic).
- L'utilisateur découvre ces outils : **expliquer** les outils et les choix pour qu'il puisse trancher.
- Fournir du code complet et fonctionnel, **bien documenté** (code et `docs/`).

## Consignes techniques

- **Code en anglais, commentaires en français** (décision de l'utilisateur, branche `refactor/code-en-anglais`) : noms de variables, fonctions, classes, fichiers et dossiers, adresses de l'API et champs JSON, tables et colonnes, valeurs des listes fermées, clés Helm, options et variables des scripts et de la CI, classes CSS. Restent en français : commentaires, docstrings, documentation, textes affichés (écrans, messages d'erreur, onglets et colonnes du fichier Excel), titres des requêtes Bruno, données d'exemple. Lexique : [docs/glossaire.md](docs/glossaire.md).
- Tout le code de l'API est dans `backend/`. Python 3.14, géré par uv.
- L'interface web est dans `frontend/` : **Next.js 16 + React 19 + TypeScript** (strict), CSS maison (`app/styles.css`), sans bibliothèque de composants. Node 26 (MacPorts sur le poste de l'utilisateur ; dans un shell non interactif, ajouter `/opt/local/bin` au PATH). **Le navigateur ne parle jamais à l'API** : le serveur Next.js la lit (`lib/api.ts`, `API_URL`), calcule l'état (`lib/state.ts`) et écrit via des Server Actions (`app/edit/actions.ts`, entrées vérifiées). Garder le maximum en composants serveur ; `"use client"` seulement pour l'interactif. Jamais l'adresse de l'API dans une page. Qualité : `npm run typecheck` et `npm run build` doivent passer.
- **API** : respect strict des méthodes REST et des codes retour HTTP. Méthodes : GET, HEAD, OPTIONS (204 + `Allow`), POST (201 + `Location`), PUT (remplacement complet, 200, 404 si absent), PATCH, DELETE (204). Codes : 400 (illisible), 404, 405 (+ `Allow`), 409, 415 (pas du JSON), 422 (contenu invalide). Règles communes dans `app/http.py`. Voir [docs/api.md](docs/api.md).
- **Toujours mettre à jour la doc** (`README.md`, `docs/`, ce fichier) avec le code.
- Une ressource = un fichier dans `backend/app/routes/` + un fichier de tests.
- **Règle d'or de l'utilisateur : on ne peut pas saisir quelque chose d'incohérent**, et ça vaut pour tout. Toute saisie qui rendrait les données fausses est refusée (409 ou 422), avec un message clair. Les règles d'ensemble sont dans `app/consistency.py` (essai sur une copie avant d'appliquer) : cluster du même type que l'environnement, pas de snapshot en prod, modules requis présents (même sans condition de version) et compatibles.
- **Projet neutre** (demande de l'utilisateur) : aucune référence à une entreprise (nom, service informatique, codes internes) dans le code, les tests, la doc ou les exemples : environnements d'exemple `int`, `rec`, `preprod`, `prod` ; zones réseau `dmz`, `interne`, `partenaires`, `admin`, `devops` ; code d'application de 3 caractères = **trigramme**. Les commentaires `--comment:` des changements Liquibase ne comptent pas dans leur empreinte (vérifié) : on peut les corriger, jamais le SQL.
- **Namespaces** : uniques par application + environnement + **cluster** + suffixe (le même nom une fois par cluster, Liquibase 011) ; l'interface affiche le cluster à côté du nom.
- Unicité toujours vérifiée **au sein de l'application** (sauf l'identifiant d'application, unique partout).
- **Tout en minuscules** : codes, identifiants, trigrammes, suffixes sont convertis en minuscules.
- **Réglages par variables d'environnement**, lus au lancement, jamais en dur dans le code (une même image Docker pour toutes les instances). Backend : `app/settings.py` (`APP_HOST`, `APP_PORT`, `APP_LOG_LEVEL`, `APP_DOCS` ; base : `APP_DB_HOST`, `APP_DB_PORT`, `APP_DB_NAME`, `APP_DB_SCHEMA`, `APP_DB_USER`, `APP_DB_PASSWORD` ; tests sur une base : `TESTS_DB_*`, nom finissant par `_tests` ; connexion : `APP_KEYCLOAK_URL` (interne), `APP_KEYCLOAK_REALM`, `APP_KEYCLOAK_CLIENT_SECRET`, `APP_FRONTEND_URL`, `APP_API_URL`). Noms des variables en anglais, le reste en français. Frontend : `API_URL`, `PORT`, `INSTANCE_NAME`, `INSTANCE_COLOR`, `APP_FRONTEND_URL`, `KEYCLOAK_URL`, `KEYCLOAK_REALM` (`frontend/lib/settings.ts`, lus au lancement du serveur Next.js ; `PORT` sur la ligne de commande en dev). Keycloak : `KC_DB_*`, `KC_HOSTNAME` (= `APP_FRONTEND_URL/auth`), `KC_BOOTSTRAP_ADMIN_*`, et pour l'import `APP_ADMIN_PASSWORD`, `APP_KEYCLOAK_CLIENT_SECRET`.
